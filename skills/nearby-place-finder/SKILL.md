# 周边探索推荐 Skill

## 一、用途与适用场景

**用途**：把用户一句话的出行需求，转成"高德真实地点 + 高德真实步行路线 + 可读的推荐结论"，让用户一次看清去哪、怎么走、要走多久。

**适用场景**：
- 从明确起点（坐标或地标）出发，找周边某一类地点：咖啡馆、餐厅、公园、书店、便利店等。
- 需求带硬性约束：步行时间上限、推荐数量上限、"优先近一点"类排序偏好。
- 单轮问答式推荐，各推荐地点都是从同一起点出发的**独立备选**。

**不适用场景**（超出本题范围，遇到时一句话说明并停止，不要自行扩展）：
- 多站点串联行程规划（"先喝咖啡再逛公园再吃饭"的一日路线）。
- 驾车、公交、地铁等非步行方式的路线查询。
- 设备实时定位（评测会提供起点坐标，本 Skill 不实现定位）。
- 订座、下单、支付等交易操作。
- 长期记忆、多轮反馈、跨城市经验迁移（非必做项，不实现）。

## 二、数据真实性红线（优先级最高，任何时候不得突破）

| # | 红线 | 说明 |
|---|---|---|
| 1 | 只写工具返回过的数据 | 地点名称、地址、经纬度、距离、时间，必须逐字来自高德地点搜索 / 步行路线规划的返回结果。不得凭常识、印象或模型知识补全。 |
| 2 | 步行时间必须来自路线规划 | **禁止**用直线距离、地图测距或"半径估算"替代步行距离与耗时。没有路线规划返回值的地点，一律不得作为符合条件的推荐。 |
| 3 | 未核实信息必须标注 | 营业状态、是否排队、安静程度、口味、评分、人均消费、停车、无障碍等高德结果字段未提供的信息：要么不提，要么明确写"未核实"。禁止任何推测性断言。 |
| 4 | 无结果如实说 | 检索范围内没找到，就说没找到，并给出放宽建议。**不得**为凑数量而放宽条件、更换品类或虚构地点。 |
| 5 | 调用失败如实说 | 高德工具报错或超时，就说明服务调用失败，不输出任何虚构地点和路线。 |
| 6 | 不携带密钥 | 回答与文件中都不出现 API Key。密钥由运行环境注入，本 Skill 不做任何密钥配置。 |

## 三、需求解析

本 Skill 面向**单轮评测**，不向用户追问。要素缺失时按下表取缺省值，并在回答的补充说明里用一句话写明所做假设。

| 要素 | 识别方式 | 缺省值 / 处理 |
|---|---|---|
| 城市 | 用户文本中的城市名 | 有起点坐标即可，城市名仅用于核对；坐标与城市明显不符时，在说明中标注"起点坐标与所述城市可能不一致"。 |
| 起点坐标 | 评测提供的经纬度，按高德 `lng,lat`（经度在前）顺序使用 | 缺失或非法（超出取值范围、非数字）时，说明无法计算步行路线，不输出推荐。 |
| 地点类型 | 关键词，如"咖啡馆""餐厅""公园" | 无法判定时不猜测具体品类，说明"未识别到明确的地点类型"并给出可检索的示例品类。 |
| 检索关键词 | 原词 + 1~2 个同义扩展（"咖啡馆/咖啡厅"、"公园/湿地公园"、"餐厅/美食"） | 只用原词检索一次，结果不足再扩展。 |
| 步行时间上限 | "不超过 15 分钟""走 10 分钟以内" | 未给出时不设硬上限，按真实步行耗时由近到远取前 3 个，并说明"未设定时间上限，按距离优先"。 |
| 推荐数量 | "最多 3 家""推荐 2 个" | 默认 3，绝对上限 3（题目要求）。用户要求更多时仍最多输出 3，并说明本 Skill 上限为 3。 |
| 排序偏好 | "优先近一点""快到的先说" | 默认按步行耗时升序。偏好涉及无法从工具返回取到的字段（安静、环境好、不排队）时，退回按步行耗时排序，并明说"缺少可用于排序的XX数据（未核实）"。 |

**品类 typecode 参考**（仅当工具支持该入参时使用；以工具字段说明为准，不确定就只用关键词检索）：咖啡馆 `050500`、公园 `110100`、餐厅/中餐 `050000`。检索后必须用返回的 `type`/`name`/`address` 字段复核类型是否真的匹配。

## 四、执行流程

### Step 1 · 把时间上限换算成检索半径

步速取 **80 米/分钟**，路网绕行系数取 **1.25**，即 **每 1 分钟约对应 100 米直线半径**；结果向上取整到 100 米，并限制在 1000–5000 米之间。

| 步行时间上限 | 检索半径 |
|---|---|
| 10 分钟 | 1000 米 |
| 15 分钟 | 1500 米 |
| 20 分钟 | 2000 米 |
| 30 分钟 | 3000 米 |
| 未给出 | 2000 米 |

半径只是**检索范围**，不是判定依据。是否达标一律看 Step 3 的真实步行耗时（路网距离通常大于直线距离，所以半径要留冗余，宁大勿小）。

### Step 2 · 高德地点搜索（查候选）

- 入参：起点坐标 + 关键词（必要时带 typecode）+ 半径 + 分页取足量结果。
- 候选池规模 ≥ 目标数量的 3 倍（目标 3 个就至少攒 6~9 个候选），按 `id`/名称+坐标去重。
- 类型复核：名称与类型字段需与用户品类吻合，剔除明显误命中（如搜"咖啡馆"返回便利店、民宿、连锁烘焙门店）。
- 结果不足或质量差：半径放大一档重试一次（最多 2 次搜索调用），仍不足则进入"结果不足"分支。
- 对候选按直线距离升序保留前 8~10 个，用于下一步路线查询（**这只用于省调用，最终排序与筛选必须依据真实路线数据**）。

### Step 3 · 高德步行路线规划（查真实耗时）

- 对每个候选调用步行路线规划：`origin` = 起点坐标，`destination` = 候选点坐标。
- 记录每个候选的步行距离与预计耗时；返回单位为秒时换算成分钟并**向上取整**（例：763 秒 → 13 分钟）。
- 候选较多时，并行/连续调用以缩短耗时；某个候选路线查询失败，重试 1 次；仍失败则标记"路线未获取"，该候选**不得进入推荐**，并在说明中点名。
- 硬过滤：预计步行耗时 > 时间上限的候选，一律排除，不得列为符合条件的推荐。

### Step 4 · 排序与截取

1. 保留：类型匹配 + 路线数据齐全 + 耗时 ≤ 上限 的候选。
2. 排序键：按用户偏好；"优先近一点"及默认情况均按**步行耗时升序**（耗时并列时取步行距离更短者）。
3. 截取前 N 个（N = min(用户要求数量, 3)）。
4. 排序结果必须与展示的距离/时间数值单调一致，不得出现"推荐理由说更近、但数值更大"的矛盾。

## 五、回答格式

固定三段：**一句结论 → 推荐表格 → 补充说明**。

**1）结论句**：一句话交代"从起点到几家、什么品类、按什么条件筛的"。例：
> 在你当前位置步行 15 分钟内，找到 3 家符合的咖啡馆，已按步行耗时由近到远排列。

**2）推荐表格**（表头固定，顺序不得调换）：

| 序号 | 地点名称 | 地址 | 预计步行距离 | 预计步行时间 | 推荐理由 |
|---|---|---|---|---|---|
| 1 | 高德返回的名称 | 高德返回的 address | 例 480 米 | 例 7 分钟 | 只用路线数据 + 类型 + 位置描述支撑 |

- 距离展示：小于 1000 米写"XXX 米"，否则写"X.X 公里"（保留一位小数）。
- 推荐理由**只允许**基于：步行距离/时间、地点类型、地址或所处位置线索、高德返回字段体现的特征。禁止编造口味、环境、评分、人均、是否营业。
- 地址字段缺失时写"地址未提供（未核实）"，不得凭坐标自行编造路名。

（示意：表格结构如下，实际数值一律以工具返回为准）

| 序号 | 地点名称 | 地址 | 预计步行距离 | 预计步行时间 | 推荐理由 |
|---|---|---|---|---|---|
| 1 | 示例咖啡馆 | 某区某路 XX 号 | 480 米 | 7 分钟 | 步行可达的最近一家，类型为咖啡厅 |

**3）补充说明**（按需，简短，1~3 行）：
- 检索口径：关键词、半径、时间上限、候选数与实际查询数。
- 未核实项清单：如"营业状态、是否需排队：未核实"。
- 所作假设：仅在要素缺失时写。

## 六、异常情况处理

| 情况 | 处理方式 |
|---|---|
| 检索范围内完全没有匹配地点 | 如实说明"在 X 米范围内以'关键词'未检索到符合条件的地点"，不输出任何虚构推荐；给出具体放宽建议（扩大半径至 Y 米 / 时间上限放宽至 Z 分钟 / 换用相邻品类关键词）。 |
| 符合条件（未超时）的地点不足 N 个 | 只推荐实际符合条件的 X 个，明确说明"符合条件的仅 X 家，不足 N 家"，不凑数、不放宽硬条件。 |
| 时间上限内无结果，但半径内有更远的地点 | 可额外列出最近 1~2 家作为**参考**，必须单独成行标注"⚠️ 超出步行时间上限（实际约 M 分钟），未计入上方推荐"，绝不能混入推荐表格。 |
| 地点搜索成功但全部路线规划失败 | 视为未获得有效路线数据：说明步行路线查询失败，只可告知"检索到 X 个候选（名称/地址来自高德）"，不得给出任何距离与时间，也不得称为推荐。 |
| 个别候选路线失败（重试 1 次后仍失败） | 排除该候选，在补充说明中点名"某地点步行路线未获取，未纳入推荐"。 |
| 高德工具报错 / 超时 | 重试 1 次；仍失败则明确告知"高德服务调用失败（地点搜索 / 步行路线规划）"，并建议稍后再试或放宽条件。**已拿到的部分数据可如实展示并标注获取到哪一步**。 |
| 起点坐标缺失或非法 | 说明缺少有效起点坐标、无法计算步行路线，不输出推荐。 |
| 候选信息不足以确认品类 | 排除，或保留但标注"类型未核实"，不得当作完全符合条件。 |
| 用户要求超过 3 个 | 最多输出 3 个，说明"本 Skill 单次最多推荐 3 家"。 |

## 七、输出前自检清单（逐项确认后再作答）

- [ ] 推荐数量 ≤ 用户要求数量，且 ≤ 3。
- [ ] 表中每一行都有高德返回的名称、地址（或标注"未提供/未核实"）、真实步行距离、真实步行时间。
- [ ] 没有任何一行的步行时间超过用户给定的上限；超时地点只可能出现在带"⚠️ 超出上限"标注的参考区。
- [ ] 排序方向与展示的耗时/距离数值单调一致。
- [ ] 推荐理由没有超出工具数据；营业状态、排队、安静程度、评分、人均等未被断言，或已标"未核实"。
- [ ] 结果不足、字段缺失、调用失败三类情况已按第六节给出如实说明与放宽建议。
- [ ] 回答中不含 API Key 等凭据信息。
- [ ] 各地点表述为同一起点的独立备选，未串成多站行程。

## 八、执行纪律

1. 顺序不可颠倒：**先搜索、后路线规划、再筛选**，不允许跳过路线规划直接按距离推荐。
2. 只使用高德 MCP 提供的地点搜索与步行路线规划两项能力，不调用未在环境中提供的能力。
3. 全流程不向用户追问，缺省即假设、假设即声明。
4. 回答面向"帮助用户做决定"：简洁、结论先行，不复述工具原始报文、不展示内部推理过程。
5. 数据存疑时从严：只信工具返回值，任何无法从返回值支撑的描述一律不写或标注未核实。
